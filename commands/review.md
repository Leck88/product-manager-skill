# 命令：/评审

## 触发方式
- `/评审`
- "需求评审"、"帮我主持评审"、"准备评审"

## 执行步骤

### 评审前准备

#### Step 1：评审自查清单
在提交评审前，帮用户过一遍 PRD 自查清单：

```markdown
## PRD 评审前自查

**完整性检查**
- [ ] 每个功能都有用户故事
- [ ] 所有功能都有验收标准（AC）
- [ ] 主流程和异常流程都已覆盖
- [ ] 字段说明完整（类型、必填、校验规则）
- [ ] 非功能需求已明确（性能、安全、兼容性）

**清晰度检查**
- [ ] 没有模糊描述（"尽快"、"及时"、"合理"等词语已替换为具体数字）
- [ ] 业务规则无歧义
- [ ] 边界清楚（什么做，什么不做）

**可测试性检查**
- [ ] 每条 AC 都可以写成测试用例
- [ ] 异常场景有明确的处理方式

**依赖检查**
- [ ] 依赖其他模块的地方已标注
- [ ] 第三方依赖已确认可用

**遗漏检查**
- [ ] 数据埋点需求
- [ ] 上线计划和回滚方案
- [ ] 权限/角色控制（如适用）
```

### 评审中主持

#### Step 2：评审会议主持框架

```
评审会时间：60-90分钟

[0-10min] 背景对齐
  - 为什么做这个功能（Why）
  - 目标用户和使用场景

[10-50min] 功能逐条走读
  - 主流程演示
  - 异常场景说明
  - 重点功能深挖

[50-70min] 疑问和风险暴露
  - 研发：技术可行性？工作量？
  - 测试：测试难点？
  - 设计：体验问题？

[70-90min] 确认和行动项
  - 明确修改项
  - 记录待确认问题
  - 确认下一步计划
```

#### Step 3：收集评审意见模板

| # | 提出人 | 类型 | 描述 | 处理方式 | 负责人 | 状态 |
|---|--------|------|------|---------|--------|------|
| | | 修改/确认/延后 | | | | 待处理 |

```markdown
**待修改项**（必须在开发前解决）：
1. 
2. 

**待确认问题**：
| # | 问题 | 负责人 | 截止 |

**评审通过条件**（如果是条件通过）：
- [ ] 修改项1 完成
- [ ] 修改项2 完成

**开发启动时间**：YYYY-MM-DD
```
